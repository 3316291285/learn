# 讲解会话：Agent 记忆系统（agent-core · agent-memory）

> 日期：2026-11-24 · 阶段 1 第 3 个概念 · 讲解对象：Vue3+TS 前端开发者，有 Dify 工作流经验
> 前置衔接：agent-loop 的递归入口 B 已立骨架（短期记忆三策略）；本讲聚焦**长期记忆的完整生命周期**

---

## 一、定位：它是什么，为什么是基石

**记忆 = 让无状态模型在"单个上下文窗口"之外保持连贯。**

一句话记住：**短期记忆解决"这个会话内怎么装得下"（截断/压缩/检索三策略），长期记忆解决"跨会话怎么记得住"（外部存储 + 按需检索注入）。**

图谱位置：

```
tool-calling → agent-loop → agent-memory ★你在这里 → mcp → multi-agent → agent-evaluation
context-window（姊妹概念：窗口大小、tokenizer 计费、管理细节）
```

与 agent-loop 的接缝（B 入口已讲）：记忆管理是 loop 内的一个钩子——`messages = maybeCompress(messages)`——不是一个独立系统。

## 二、核心机制：长期记忆的完整生命周期

```
写 Write → 存 Store → 检 Retrieve → 注 Inject
```

**① 写什么——三类记忆（对照人类记忆分类）**

| 类型 | 记什么 | 例子 |
|---|---|---|
| 情景记忆 episodic | 发生过的事 | 会话摘要、"上次用户报过 X bug" |
| 语义记忆 semantic | 提炼出的事实 | "用户是 Vue3 开发者"、"项目用 pnpm" |
| 程序记忆 procedural | 学到的操作技能 | "这个工具的日期参数要传 UTC" |

**② 何时写——写策略决定记忆质量**
- 会话结束（或每满 N 轮）：由 LLM 提炼"值得长期记住的事实"再写入（最常用）
- 显式指令：用户说"记住我喜欢 X"
- 规则触发：同一错误回传出现 ≥2 次 → 记住这个坑
- **不是每轮都写**！什么都记 = 检索时全是噪声

**③ 怎么存**
- 结构化记录（JSON 条目）/ key-value / 向量库（embedding）/ 知识图谱
- 选择标准：检索精度需求 vs 维护成本——小规模结构化即可，别一上来就上向量库

**④ 怎么检**
- query（当前用户输入/任务）→ 相似度 top-k → 返回片段
- 记忆量小可以全量注入；大了才需要检索

**⑤ 怎么注**
- 注入 system prompt（最常见）或作为消息前缀
- 注入也有成本：**记忆不是越多越好**——噪声稀释注意力，和"工具过多"是同一个权衡

## 三、类比锚点

- **操作系统**（B 入口已立）：短期 = 内存、长期 = 磁盘；检索 = 按需换页（demand paging）；注入 = 页面调入；写策略 = 脏页回写时机。
- **前端（Pinia）**：长期记忆 = 跨"页面"（会话）共享的全局 store；写策略 = watch + debounce（不是每次变化都持久化）；检索 = computed 按需求值。
- **Dify**：知识库检索节点 = 语义记忆的检索式实现；会话变量 = 短期记忆的结构化版。
- **DSH**：持久化插件（dynamic-cordis）= 给 agent 平台装"磁盘"——你二开时给场景智能体做记忆，就是写一个带持久化的 cordis 插件。

## 四、代码示例：最小长期记忆骨架（阅读向）

```typescript
interface MemoryItem {
  type: "episodic" | "semantic" | "procedural";
  content: string;
  createdAt: number;
  source?: string;          // 来源会话/概念，便于溯源与过期清理
}

interface MemoryStore {
  write(item: MemoryItem): Promise<void>;
  search(query: string, k: number): Promise<MemoryItem[]>;  // 小规模可用关键词，大了换 embedding
}

// ── 注 + 检：每次请求前，检索相关记忆拼进 system ──
async function buildMessages(userMsg: string, store: MemoryStore) {
  const hits = await store.search(userMsg, 3);              // 检：top-3
  const note = hits.map(m => `- [${m.type}] ${m.content}`).join("\n");
  return [
    { role: "system", content: `已知长期记忆：\n${note}\n\n${BASE_SYSTEM}` },
    { role: "user", content: userMsg },
  ];
}

// ── 写：会话结束时由 LLM 提炼（写策略的核心）──
async function distill(session: ChatMessage[], store: MemoryStore, llm: ChatClient) {
  const resp = await llm.create([
    { role: "user", content: "从这段对话提炼值得长期记住的事实（用户偏好/项目约定/踩坑教训），每条一行，没有则返回空：" },
    ...session,
  ]);
  for (const line of (resp.content ?? "").split("\n").filter(Boolean)) {
    await store.write({ type: "semantic", content: line, createdAt: Date.now() });
  }
}
```

两个设计决策值得品味：
1. **写入走 LLM 提炼而非原文存档**——存的是"语义记忆"不是"聊天记录"，信息密度高一个量级。
2. **检索 top-k 而非全量注入**——记忆条数一多，全量注入等于自己造了个窗口溢出。

## 五、常见误区

1. **"记越多越聪明"** —— 注入噪声稀释注意力，模型反而变笨。记忆系统的功夫在"少而准"，与"工具不是越多越好"同一权衡。
2. **"记忆永远有效"** —— 用户偏好会变（上周美式今天拿铁）。旧记忆要能被**覆盖更新**（按主键 upsert），否则新旧冲突时模型随机听一条。
3. **"向量相似 = 相关"** —— embedding 抓语义相似，抓不住任务相关性。检索结果要限流过滤，必要时二次排序。
4. **"记忆无隐私问题"** —— 跨会话持久化 = 敏感数据留存。要有清除机制（用户可删）、分级（哪些可记哪些不可记）。

## 六、苏格拉底自检（开放式纯问答）

**Q1（判断对错）**："记忆条目应该尽量多存、检索时尽量多注入，因为上下文越丰富模型回答越准。"——对吗？为什么？

**Q2（场景设计）**：用户上周说"我喝美式"，今天说"改喝拿铁了"。记忆系统应该怎么处理这条旧记忆？如果两条都留在库里会发生什么？

a) "2026-11-20 用户让我批量重命名过一次组件文件"
b) "用户项目的组件命名用 PascalCase"
c) "调用 rename 工具时 dry_run 参数要先设 true 试跑"

## 七、递归入口

- **A. 存储深挖**：embedding/向量检索原理 → 接 `structured-output`（记忆条目的结构化校验）
- **B. 姊妹概念**：`context-window` 正式讲（tokenizer、计费、窗口管理细节）——B 入口的展开
- **C. 主线**：图谱顺序下一个概念 `mcp`

## 讲解小结

- 记忆生命周期 = 写→存→检→注；功夫在**写策略（少而准）**和**注入克制（top-k）**。
- 三类记忆：episodic（事）/ semantic（事实）/ procedural（技能）。
- 短期靠三策略，长期靠外部存储 + 按需检索注入——都是 loop 的钩子，不是独立系统。
- 记忆有维护成本：过期覆盖、隐私清除——和依赖管理一个道理，存进去容易，管好很难。

## 苏格拉底问答记录（学习者作答 · 2026-11-24）

**Q1（多存多注入判断）✅ 正确**：错——越多噪声越多、越易幻觉。机制补充：每条注入占 token 且稀释注意力权重，"上下文丰富"实际是"注意力稀释"。

**Q2（覆盖更新）✅ 正确 + 极佳追问**：覆盖正确；两条并存 → 冲突、模型随机取一条。学习者追问"是否覆盖是否应该由模型判断（如思考上周的美式记忆是否还值得留存）"——正解详见下方澄清小节：是的，生产系统把记忆管理做成模型可调用的工具（add/update/delete/search，MemGPT/Letta 模式），且区分 semantic 当前值（UPDATE）与 episodic 历史（ADD）两层。

**Q3（三分类）✅ 全对**：a-episodic / b-semantic / c-procedural，三个定义复述准确（情景=对话场景、语义=项目关键事实、程序=学到的操作约束）。

**置信度**：0.3 → 0.4。

## Q2 追问澄清：记忆的"覆盖决策"交给谁

学习者的直觉完全正确：**"是否覆盖"是判断题，判断就该交给模型**。生产系统的做法：

1. **记忆管理即工具调用**：给模型一组记忆操作工具 `add / update / delete / search`，提炼记忆时模型自己发指令——"把《用户喝美式》UPDATE 为《用户喝拿铁》"。MemGPT/Letta 是这套模式的代表。这正是前两个概念的组合应用：tool-calling（模型发意图）+ agent-loop（循环中反复读写）= 自管理记忆。
2. **区分两层，历史不丢**：semantic 条目"用户当前喝拿铁"（UPDATE 覆盖当前值）+ episodic 条目"口味从美式变为拿铁"（ADD 追加历史）。要"思考是否留存上周的记忆"时，答案是分层：事实只留最新，历史按需保留（偏好演变本身有时是有用信号）。
3. **兜底**：即使漏覆盖了，system prompt 里可注明"记忆冲突时以时间戳新者优先"。

## 递归入口 A：存储深挖（embedding/向量检索 → structured-output 桥接）

### A-1 embedding 是什么

把文本映射成高维向量（如 1536 维浮点数组），**语义相近 → 向量距离近**。类比前端：像把组件编码成特征数组，props/用途越像的组件数组越像。关键性质：字面完全不同的两句话（"怎么装 Dify" vs "Dify 部署教程"）向量距离很近——它编码的是语义不是字形。

### A-2 向量检索全流程

```
写入：文本 → embedding 模型 → 向量 → 入库（附元数据 type/source/createdAt）
查询：query → 同一个 embedding 模型 → 向量 → 库内找最近邻（余弦相似度）→ top-k
```

- **余弦相似度**：两向量夹角的余弦，1 = 同向。
- **ANN 近似最近邻**（HNSW 等索引）：牺牲一点精度换毫秒级检索。但小规模（几万条以内）暴力算余弦完全够用——呼应"小记忆别上向量库"。
- **铁律：写入和查询必须用同一个 embedding 模型**（见小检 1）。

### A-3 分块 chunking——决定检索质量的第一要素

长文档要先切块再 embedding：块太大 → 一块混多主题、向量语义被平均稀释；块太小 → 上下文碎片化。常用：按段落/标题切，200–500 token/块，块间重叠 10–20%。

### A-4 桥接 structured-output

记忆条目是结构化数据，但 LLM 提炼输出不稳定（字段名漂移/缺字段）→ 用 schema 约束：

```typescript
import { z } from "zod";
const MemoryItemSchema = z.object({
  type: z.enum(["episodic", "semantic", "procedural"]),
  content: z.string().min(1),
  source: z.string().optional(),
});
// distill 的输出：JSON mode 请求 → zod.safeParse → 失败则把校验错误回传模型重试（错误即观察！）
```

结构化输出 = 给模型输出套 schema 约束，本质和 tool calling 的参数约束是同一机制的两面——正式讲在 `structured-output` 概念。

### A-5 检索错配的三个缓解（呼应误区 3）

1. **元数据过滤**：先按 type/source/时间筛小集合，再向量检索。
2. **混合检索**：关键词（BM25）+ 向量双路召回，RRF 合并排名。
3. **重排 rerank**：向量粗排 top-20 → rerank 模型精排 → top-3 注入。

### 入口 A 小检（读码判断 × 2）

**检 1**：为什么写入记忆和查询时必须用**同一个** embedding 模型？如果写入用模型 X、查询用模型 Y（不同厂商，甚至维度都不同），会发生什么？

**检 2（场景）**：记忆库 500 条，用户问"上次那个组件重命名的事"，纯向量检索返回的 3 条都是"组件"相关但没命中"重命名事件"。给出至少两个提升命中率的手段。

### 入口 A 小检批改（学习者作答 · 2026-11-24）

**检 1（同模型铁律）✅ 方向正确，机制补锐**：答"两套向量规则不一致 → 查询有误差，同模型更稳定"。锐化：不是"误差"，是**完全无意义**——不同 embedding 模型把文本映射进**不同坐标系**，即使维度相同，每个坐标的含义也不同，算出的相似度是噪声；维度不同则连余弦都算不了。补充工程细节：同一厂商升级 embedding 版本（v2→v3）同样破坏铁律——向量库通常把"模型名+版本"存进元数据，换模型 = 全量重嵌入迁移。

**检 2（检索 miss）⚖️ 一半对，一半混淆了阶段**：
- 方案 1"不用向量库、换其他存储"→ **有效方向**。500 条规模关键词检索（BM25/标签）完全够用，query 里"组件""重命名"是强关键词——正是 A-5 缓解 2 的适用场景，呼应"小记忆别上向量库"。
- 方案 2"上下文太多→压缩"→ **混淆了检/注两个阶段**。失败发生在**检**（没召回目标条目），压缩作用在**注**（注入后降噪）——压缩再狠也救不回没被检索到的条目。可挽救的正核：写入时**条目粒度太粗**，"重命名事件"被大杂烩条目淹没 → 写入侧按"一事一条"切细（chunking 思想）。

**完整方案清单**（按生产性价比排序）：
1. **查询改写**：LLM 先把口语 query 改写成检索友好型（"上次那个组件重命名的事" → "批量重命名 组件 文件"）再检索——生产 RAG 第一杀手锏（HyDE/查询扩展同理）。
2. **混合检索**：BM25 + 向量双路召回，RRF 合并——关键词直接命中。
3. **元数据过滤**：按 type=episodic + 时间范围（"上次"暗示近因）先筛再检。
4. **时间加权**：检索分数加 recency 权重，新条目加分。
5. **rerank 精排**：粗排 top-20 → rerank 模型精排 → top-3。
6. **条目粒度优化**（方案 2 的正核）：写入时就"一事一条"。

**入口 A 关闭**。置信度 0.4 → 0.45。
